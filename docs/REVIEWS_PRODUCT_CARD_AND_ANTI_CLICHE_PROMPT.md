## Task 1 — Ban generic AI heading clichés and push past the first-instinct phrasing

### Goal
Subheaders and taglines must never use the stock AI phrasings that a language model reaches for first (e.g. "Real people, real results"). Two mechanisms: a hard ban list, and a generation instruction that deliberately skips the most-probable phrasing.

### 1a. Add an "AI heading cliché" ban to `data/copy-system.md` (RULES section)
Add a new block under the existing "Banned structures". These apply especially to **Subheaders and Taglines** but hold everywhere. Include at minimum (literal, case-insensitive):

> "real people, real results", "real people, real reviews", "real results", "say hello to", "say goodbye to", "meet your new", "the [x] you've been waiting for", "experience the difference", "discover the difference", "hear the difference", "feel the difference", "because you deserve", "it's time to", "the future of", "reimagined", "perfected", "sound that moves you", "music to your ears", "where [x] meets [y]", "everything you need, nothing you don't", "the only [x] you'll ever need", "good [x] just got better", "just got better", "turn up the", "life, but better", "[x], elevated", "[x], reinvented"

(These sit alongside the already-banned "elevate", "next-level", "game-changer", "unleash", "It's not X, it's Y", and the "Adjective Noun. Adjective Noun." anaphora.)

### 1b. Add the "reach past your first instinct" directive
In `data/copy-system.md` VOICE (or the `generateRoleInstruction` element-craft notes in `src/lib/prompts/generate.ts`), add for Subheaders and Taglines:

> The first phrasing that comes to mind for a heading is almost always the statistically most common, most obviously AI option. Generate at least 5 candidates internally, discard the 2 to 3 most predictable/cliché ones, and choose from the less-obvious remainder, as long as it stays specific, concrete, and on-brand. Never ship anything on the AI heading cliché list.

The Subheader element already emits 3 distinct options (see the generate JSONL shape) — reinforce that each must clear the cliché bar, strongest-first.

### 1c. Enforce mechanically in `src/lib/hard-rules-check.ts`
- Add the literal cliché phrases to a new `BANNED_HEADING_CLICHES` list and check them (case-insensitive substring) on all text.
- Add 3 to 5 regex patterns for the templated ones, e.g. `/the\s+.+\s+you'?ve been waiting for/i`, `/say (hello|goodbye) to/i`, `/(experience|discover|hear|feel) the difference/i`, `/\b\w+,\s+(reimagined|perfected|elevated|reinvented)\b/i`.
- These are **flag-level** (not auto-fixable). Surface them through the existing report path so the client toast shows them.
- Update `data/copy-system.md` SELFCHECK to add: "No AI heading clichés in any subheader or tagline."

### Acceptance criteria
- [ ] "Real people, real results" (and the rest of the list) are rejected/flagged wherever they appear.
- [ ] Checker unit-tested with a couple of cliché strings → flagged; clean headings → pass.
- [ ] `npx tsc --noEmit` clean.

## Task 3 — Fetch a real review from the product page

### Goal
Whenever a section includes a review (`reviews` and the new `product_card_review`), the app pulls a REAL review for that product and feeds it into generation. No fabricated reviews, ever (this is already a hard rule).

### 3a. Find the review data source (discovery step — do this first)
The catalogue product URLs live in `data/products.md` (e.g. `https://rayconglobal.com/products/the-everyday-earbuds`). Determine where the real reviews actually come from, in this priority:
1. **Shopify** — a Shopify MCP connector is configured for this workspace. Check whether product reviews are exposed via Shopify (product metafields, or a reviews app's data) using the Shopify Admin GraphQL. If reviews live in metafields, read them there.
2. **Review-app JSON endpoint** — Raycon's product pages likely use a reviews widget (Judge.me / Okendo / Yotpo / Loox). These expose a JSON/API endpoint. Inspect one product page's network requests (Claude in Chrome, or browser devtools) to find the reviews endpoint and its response shape.
3. **Rendered page scrape** — only if the above fail: the reviews are JS-rendered, so a plain server fetch will not see them; a rendered fetch (Claude in Chrome) would be needed. Treat this as the last resort.

Document which source you used.

### 3b. Build the review service
Create `src/lib/reviews/fetch.ts` (or similar) with a clean interface:
```ts
export interface ProductReview { text: string; rating?: number; author?: string; date?: string; }
export async function fetchProductReviews(productId: string, opts?: { limit?: number }): Promise<ProductReview[]>;
```
- Map `productId` (SKU like `E25`) → product URL / handle. Add a `url` (or `handle`) field to `PRODUCT_CATEGORIES` in `src/lib/products.ts`, sourced from `data/products.md`, so the mapping lives in code.
- Prefer high-rated, substantive reviews (e.g. 4 to 5 stars, a sentence or two, in English). Return an empty array if none found.
- **Cache** results to `data/reviews/<productId>.json` so you are not refetching on every generation and so the team can curate/override. Add a route `GET /api/reviews?product=E25` that reads cache, fetching (and caching) on miss.

### 3c. Wire reviews into generation
- Before generating a campaign that contains a `reviews` or `product_card_review` section, fetch reviews for the relevant product(s) and pass them into the prompt as **supplied, must-use, verbatim** content (same channel as `hero_angle_verbatim` — the user's literal instructions tier, which already outranks everything).
- For a `reviews` section, supply up to 3 reviews (one per Review element). For `product_card_review`, supply the single best review for that card's product.
- The prompt must use them verbatim (light length trim allowed) and must NOT alter their meaning or invent missing ones.

### Guardrails
- **Never fabricate.** If `fetchProductReviews` returns nothing, fall back to any user-supplied review, otherwise leave the Review element empty and flag it in the UI ("no review found for this product"). Do not let the model write a fake review. This is already enforced by the hard rule "never invent reviews" and the deterministic checker; keep it that way.
- Reviews are third-party content: strip anything unsafe/PII beyond first name, and respect length caps for display.

### Acceptance criteria
- [ ] Selecting a review-bearing section pulls a real review for the product and it appears in the output.
- [ ] With no available review, the element is empty/flagged, never fabricated.
- [ ] Reviews are cached and re-used; a documented source.
- [ ] `npx tsc --noEmit` clean.

# Follow-up corrections (v2) — after the first build

The first build shipped. Four bugs surfaced in testing. Fix all four; the relevant code already exists (`src/lib/reviews/fetch.ts`, `src/app/api/reviews/route.ts`, `src/app/api/generate/route.ts`, `src/lib/schemas.ts`, `src/lib/prompts/generate.ts`, `data/copy-system.md`, `src/lib/hard-rules-check.ts`). Typecheck after each. After fixing A, delete the stale caches in `data/reviews/*.json` so they re-fetch with the new fields.

## Correction A — the review must include the reviewer's name
Right now `parseJudgeMeHtml()` in `src/lib/reviews/fetch.ts` extracts only `data-score` (rating) and `jdgm-rev__body` (text). The author is never parsed, so `ProductReview.author` is always undefined, the cache has no name, and `generate/route.ts` passes `reviews.map(r => r.text)` (name dropped).
- **Parse per-block, not by zipping separate arrays.** Split the HTML into individual `jdgm-rev` review blocks first, then pull `score`, `body`, and **author** (`jdgm-rev__author`) and optionally date (`jdgm-rev__timestamp` / `data-content-created`) from *within each block*. This also fixes the current fragile index-zip (scores and bodies can misalign if counts differ).
- Populate `ProductReview.author` (first name / "First L." only; strip surnames/PII beyond that).
- **Carry the author through generation.** In `src/app/api/generate/route.ts`, change `reviewsBySlug` from `Record<string,string[]>` to carry `{ text, author }` (or pre-format each as `"<text>" — <author>`), and update `generateUserPrompt` / `generate.ts` so the model places the review **with attribution** (e.g. ends with `— Jordan M.`). Use ONLY the real fetched name; if none, omit attribution (never invent a name — hard rule).
- **Decision (pick one, note it):** either embed `— Name` inside the `Review` string (smallest change, no render updates), OR add a separate `Reviewer` element to `product_card_review` and `reviews` in `SECTION_CATALOGUE` (cleaner, but touches the render/export paths). Recommend the embedded-attribution approach unless Tim wants the name styled separately.

## Correction B — the review must actually be about the featured product
Two parts. (Evidence: an E95 "Pro Earbuds" card generated copy about "Everyday Pro Earbuds" — not a real product — and the cached review foregrounded "everyday fitness earbuds".)
- **Pin the product name to the catalogue.** For `product_card` / `product_card_review`, the `Product Name` element must equal `getProductName(product_slug)` exactly. Set it programmatically from the catalogue rather than letting the model write it (or hard-check it and repair drift). The model must never coin variants like "Everyday Pro Earbuds". Add a checker rule: a product-card `Product Name` that is not an exact catalogue name is flagged.
- **Relevance + scoping guard in `fetch.ts`.**
  - Only parse reviews from the product's OWN Judge.me widget block, not from any "recommended products" / "you may also like" review snippets elsewhere on the page (cross-product bleed).
  - Verify the fetched page is the right product (the response did not soft-404 or redirect to a different handle).
  - Downrank or skip a review whose text prominently names a DIFFERENT catalogue product more than the featured one (that is what made the E95 review read as a Fitness Earbuds review). Prefer reviews that are clearly about the featured product.
- **Recency + positivity/no-disparagement screen in `fetch.ts` (important).** A high star rating is NOT enough. The current code ranks by rating only, with no recency and no sentiment check, which is why the E95 example slipped through: *"I love these so much. I had the everyday fitness earbuds but they began to die within two to 3 hours and the case would not hold a charge past 6 hours..."* is 5 stars but it disparages a Raycon product. We must never surface that (it also breaks the semantic-contamination hard rule about planting negative associations with a product).
  - **Prefer recent reviews.** Parse the review date (Correction A already adds date parsing) and rank the qualifying set newest-first (or rating-then-recency). Do not surface stale reviews when fresher ones qualify.
  - **Only wholly positive, clean reviews are eligible.** Exclude any review that: contains a complaint, defect, return, discomfort, or "stopped working" story even if the overall rating is high; disparages, criticizes, or unfavorably compares ANY Raycon product or the brand; or describes a problem the reader would not want associated with the product.
  - **Implement as two stages:**
    1. **Deterministic pre-filter (cheap first pass):** drop reviews containing negative-signal terms/patterns, e.g. `die|died|dying, broke|broken, stopped, wouldn't/won't (hold|charge|connect), fell out, uncomfortable, disappointed, poor, cheap, return|refund, defect, "used to", "the old ones", "previous ones", "unlike"`. Curated list; err toward dropping.
    2. **LLM positivity screen (the reliable catch):** run the shortlist through a cheap fast-model call (`FAST_MODEL` / Haiku in `src/lib/anthropic.ts`) that, for each review + the featured product, returns whether it is (a) clearly about THIS product, (b) wholly positive, and (c) free of any negative statement or comparison about any Raycon product. Keep only reviews that pass all three. This catches the "shit-talking" a keyword list misses (the E95 example fails on (b) and (c)).
  - A review is eligible only if it passes ALL of: substantive + 4 to 5 star + about-this-product + recent + positivity screen. Rank survivors newest-first and cache. If none pass, return empty (Review element left empty + flagged) — never fabricate and never surface a negative review.

## Correction C — a refresh control on the Review to pull another one
- `generate/route.ts` currently fetches `{ limit: 1 }`. Fetch a small ranked list (e.g. `limit: 5`) so alternatives exist; still place the top one by default.
- Add a **refresh icon** on the Review element (in both `reviews` and `product_card_review` sections; render lives in `src/components/SectionBlock.tsx`). Behaviour: step to the next review in the list; when exhausted (or on user demand) call `GET /api/reviews?product=<slug>&refresh=1` (already supported) to re-pull fresh from the storefront. Replace BOTH the review text and the reviewer name on each step.

## Correction D — keep the promo code (and length) out of the CTA
A CTA read "Get 30% off, code COMBO30" — too long and it embedded the code.
- **Rule** (`data/copy-system.md` RULES + SELFCHECK, and the CTA note in `src/lib/prompts/generate.ts`): a CTA is a 2 to 4 word action phrase. A discount phrase ("Get 30% Off") is allowed, but the **promo code never appears in a CTA**. Codes live in body copy, a callout, or the tagline.
- **Deterministic checker** (`src/lib/hard-rules-check.ts`):
  - Add `cta: { maxWords: 4 }` to `CAPS`.
  - Add a `cta` branch to `checkKindSpecific`: flag a promo code in a CTA — a standalone ALL-CAPS alphanumeric token (e.g. `COMBO30`) or the literal word "code" → rule `"code-in-cta"`.
  - This would have caught "Get 30% off, code COMBO30" on both counts.
